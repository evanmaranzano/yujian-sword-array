## 一、总体结论

**当前系统是一个完成度较高的"笔记本/桌面 demo"，可以用于内部演示和进场试点，但不具备 7×24 无人值守正式部署条件。**

三条主线成立，应保留：

1. **纯离线彻底**：three.js r185、MediaPipe tasks-vision 1.0.1（含 wasm/nosimd 双份）、7.8MB 手部模型全部本地 vendor，一方代码零运行时外网请求（已逐字 grep 核实），满足"无外网"硬约束。
2. **方向映射直觉正确**：掌心五点均值→坐标镜像→世界 y 翻转→CSS 镜像预览全链路自洽，Python 无头测试还有镜像方向断言守护。
3. **渲染架构健康**：双 InstancedMesh（剑芯+光晕）承载剑群，世界层 draw call 约 31~36 个；活动剑数实测估算待机约 215、连续狂挥峰值约 400~500，远低于 1500 槽位；对象全部定长池化、纹理/几何构造期一次性创建，**未发现内存/显存泄漏点**，具备长时间运行的基础。

## 三、高优先级问题（经对抗验证）

### 🔴 C1 「第一个锁定的人」未实现：numHands=1 不是锁定，围观/交接可夺控并诱发假齐发
**验证：partial → 维持 critical（置信 high）**

- **位置**：`web/js/tracking.js:95,129-145`；`yujian/tracker.py:39-43,115-133`（第 39 行注释还写着"第一个锁定的人（围观不干扰）"）；相反的保证见 `README.md:41`。
- **事实**：两版都只设 `numHands=1`，每帧直接取 `landmarks[0]`，应用层无手 ID、无最近邻关联、无锁定滞回、无 ROI。验证代理修正了一处机制表述：MediaPipe VIDEO 模式内部有跨帧跟踪，跟踪保持期间有粘性，新人**不是任意帧**都能夺控——但在跟踪丢失/遮挡/重检测的边界（3–5m 小手、快速挥臂出画时高频发生），输出会切给当前画面最显著的手。
- **后果**：① 围观者凑近/伸手、儿童跑到镜头前、工作人员路过即可夺控，本命剑横穿画面；② 换手时 EMA 不平滑复位，坐标滑变速度经核算远超 `swipeHi`（两人坐标差 0.4 时窗口速度约 1.8/s ≫ 0.75），会朝新人方向打出一记完整齐发；③ 前人未走、后人已到（间隔<0.5s）时不回待机、不重播"剑来"。与甲方书面确认的"单次单人、以第一个锁定的人为准、肯定会有围观群众"**正面冲突**，且文档给出相反保证。
- **建议**：应用层实现显式会话锁——首手在中心交互区内驻留 N 帧才锁定；锁定期间用"最近邻 + 帧间最大位移"做身份关联，非锁定手一律丢弃；身份跳变点不送挥舞检测；丢失超时后强制回待机并重新走锁定流程。构造两人入画的真机/多手脚本回归。

### 🔴 H2 追踪链路无自愈，故障外观与正常待机/交互完全相同
**验证：confirmed（置信 high）**

- **位置**：`web/js/tracking.js:110-115,116-119,122-148`；`yujian/tracker.py:86-113`。
- **事实链**：
  1. Web 追踪 rAF 中 `detectForVideo`（:128）**无 try/catch**，推理一旦抛错，末尾的 `requestAnimationFrame` 不可达，追踪链永久终止，渲染 rAF 独立存活——画面是"活着但瞎了"；
  2. USB 相机掉线/被碰松后 `video.currentTime` 冻结，:124 的门控使整个检测块（含 :143 的丢失超时）都不执行——若当时正有手交互，**`present` 永久锁存 true**，本命剑定格在最后位置、待机永不恢复（验证代理特别纠正了"停在待机"的说法：交互中掉线是定格在"有人"）；

  4. 全仓无 `track.ended`/`ondevicechange`/`stalled`/`reload` 监听；Python 侧推理异常同样直接杀死守护线程而 `alive` 仍为 True，`README.md:43`"追踪线程崩溃自动重开摄像头"只对 `cap.read()` 失败成立。
- 文档规划的外部看门狗是"白屏检测"（`web/README.md:66`），此故障既不白也不黑，**检测不到**，只有 24h 计划重启兜底。

### 🔴 H5 4K/缩放集显的分辨率与显存预算无封顶（待真机实测）
**验证：confirmed（估算偏保守，置信 medium）**

- **位置**：`web/js/main.js:23`（`setPixelRatio(min(dpr,2))` 只封 dpr 不封设备像素总量）、`:43-51`（composer 双 HalfFloat RT 且 `samples=4`，AfterimagePass 内部还有两个 HalfFloat 全屏 RT，Bloom 11 个 RT）。
- **粗算**：4K + Windows 150%/200% 缩放 → 设备像素 5760×3240 / 7680×4320；dpr=2 时两个 composer RT 各约 265MB、各挂 4 采样多采样缓冲约 1.06GB，加 afterimage 双 RT、bloom mip 链、多采样深度缓冲，**总量约 3.4GB 以上**，每帧约 5 个 8K 全屏 pass。展厅集显（WebGL 显存预算常仅 1–2GB）可能启动即黑屏、运行中掉帧或 context lost。
- 附带确定问题：`main.js:51` 给 `.samples` 赋值包的 try/catch 是**假保护**（赋数字不会抛异常），MSAA 还错加在 composer 交换 RT 上，导致每个全屏 pass 都付 4 倍带宽，而光剑/Bloom/全屏四边形完全不受益（M1-6）。
- **建议**：真机确认展厅机 GPU 型号与 Windows 缩放比例；设备像素长边硬封顶（如 2560–3200）或 kiosk 固定 100% 缩放；MSAA 改为 samples=0（暗场霓虹+bloom 下观感损失很小）或只挂场景 RT；4K 机上实测帧率与 chrome://gpu 显存，留 30% 余量；删除假 try/catch。

### 🔴 H6 kiosk 形态齐发音效必然全程无声
**验证：confirmed（置信 high，运维维度评 high）**

- **位置**：`web/js/main.js:77-101,173`。
- **事实**：`actx` 只在 `pointerdown`/`keydown` 首次事件里创建，`whoosh()` 开头 `if (!actx) return`；齐发只调 `whoosh(peak)` 不自行创建。展厅是 3–5m 空手挥手、投屏非触摸、运维不插键盘——永远没有触发事件。`--autoplay-policy=no-user-gesture-required` 只放宽浏览器策略，**不会替代码创建 AudioContext**；每日重启后再次回到无声。（笔记本试点路径下，点"允许摄像头"那次点击会顺带初始化音频，所以开发时听不出来。）

### 🔴 H7 初始化失败无恢复、无可读提示
**验证：confirmed（置信 high）**

- **位置**：`web/js/tracking.js:90-119`；`web/index.html:52`（静态"启动中…"）；`web/js/main.js:179-195`（无 `.catch`、无 `window.onerror`）。

## 五、下一步优化建议（按优先级的路线图）

> 原则：**先证伪现场可行性，再补需求级锁定，再做部署硬化**；每一步都产出可被验收的数据/脚本，而不是口头结论。

### P0 — 进场前必须完成（决定"能不能用"）

1. **现场可行性实测（半天，最高优先）**：修好 H1 的真机标定脚本 → 在真实场地（或等比模拟）3/4/5m × 成人/儿童测手掌像素尺度、检测率、手速分布、灯光影响；据此定相机型号（1080p/长焦而非广角）、安装高度俯仰、是否需要 ROI 裁剪，并反定 `swipeHi` 等阈值。没有这份数据，后续所有手感调参都是猜。
2. **实现"第一个锁定的人"（C1）**：ROI 中心交互区 + 驻留确认 + 位置连续性关联 + 非锁定手丢弃 + 跳变拒判 + 丢失强制回待机；预览窗叠加 ROI 框。用两人入画脚本/真机回归。
3. **追踪健壮性（H2+H7）**：推理全链路 try/catch、冻结帧看门狗、track ended/devicechange 退避重连、CPU 降级可视告警、中文故障遮罩、页面级超时自动 reload；Python 侧补线程防护后才有资格当备用。
4. **部署套件实物化（H3+H6+M2-5）**：kiosk 启动器 + autoplay/全屏/隐指针 + 注册表免弹窗 + 任务计划（自启/日重启）+ 独立看门狗（端口/心跳/黑帧）+ 端口就绪轮询 + 电源策略清单；音频改为启动即初始化；关闭/参数化预览窗与调试键。
5. **分辨率预算实测与封顶（H5+M1 中 MSAA/拖尾）**：在目标展厅机（含其 Windows 缩放设置）上实测帧率/显存，设备像素封顶、MSAA 归零或仅挂场景 RT、拖尾 damp 改 dt 相关。
