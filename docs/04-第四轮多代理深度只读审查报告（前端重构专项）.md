## 一、总体结论

### 1.1 一句话判断

**"交互脑"已经立住且有测试守护（会话锁正确、标定/烤机工具就位、纯离线链路零外网请求）；但"表现层"不成立——用户"太丑"的判定经逐帧截图取证完全成立，而且新发现 7×24 播放最久的待机画面中心常驻一颗语义不明的白色光斑。下一步不应继续在现有 scene.js/swords.js 上调参，而应"保留交互脑、整体重写表现层"，且这条路线已有许可证清白、可直接借鉴的开源实现（阵型算法、ribbon 拖尾、CC0 剑模、OFL 字体、选择性辉光后处理）。**

### 1.2 本轮三条主结论

1. **审美判定成立且根因是视觉语言错误，不是参数问题**：齐发瞬间糊成"白色蒲公英/海胆"（64 个加色外壳同点叠加 + 全屏帧累积 + bloom 四重成因）、本命剑像白色荧光棒、待机中心常驻白斑、aura 像靶心、冲击波像跨屏肥皂泡、远山是无光照剪纸、月亮是白饼+硬边矩形玻璃板光柱、符文是 WordArt、暗部发灰、下半屏 45% 纯黑死区。4 项致命观感缺陷（V1–V4）**只能靠表现层重写解决**；参数微调只能"不刺眼"，约 1 天工作量且不改变本质（A 代理估算）。
2. **重构可以"带着安全带换发动机"**：会话锁 lock.js、tracking.js 的锁接线与视频帧门控、config 参数体系、Python 测试链是已验证资产，重构冻结其接口、整体替换 scene/swords/表现段 main.js/HUD；B 代理给出了字段级事件契约与 P0–P6 分阶段计划，每阶段都有"截图基线 + lock_check + smoke"回归门。
3. **docs/03 的技术债台账本轮全部复核**：H1 已真实修好（质量合格，有边界缺陷）；H2–H7 **一项未动**但排序让位于重构；新发现 5 项问题（待机白斑 V1、恢复期假齐发 N-LOCK-2、smoke 高负载 flaky、Web 部署形态零烤机工具、标定工具采不到"锁不上的人群"数据）。

## 三、视觉表现层审计：用户为什么说"太丑"（本轮核心）

> 证据：A 代理 16 张无头实拍逐张实眼判读（720p 时间线 t=0.01→5.8 + 1080p + 3440 超宽），主控另实拍 live idle 坐实 V1；swiftshader 软渲与真机 GPU 在 bloom 质感上略有差异，但**几何、构图、材质形态、层级关系与渲染器无关**。

### 3.1 致命缺陷（直接决定"丑"，必须表现层重写）

**V1【致命·主控实拍坐实】待机画面正中央常驻一颗白色"蒲公英/米字星号"，与月亮形成两个太阳。**
- 现象：`?demo=1` 纯待机（无手、HUD"追踪 0"、提示待机语）运行 8s 后，画面中心（约 55%x、40%y，正压在符文"訣/靈"上）永久停着一颗白色刺球状光斑（实拍 HUD 剑光 134）；此前所有 v3 时间线截图里它也都在，被误读为"齐发残留"。
- 根因：`swords.js:120-137` idleTrickle 每帧 1 把（60/s）从屏幕边缘生成、目标锁中心 ±4 单位并带螺旋速度、寿命 2.6–3.8s（寿命硬编码，`swordLife` 死配置）→ 稳态约 **192 把剑永久在向中心螺旋汇聚并死在中心附近**；`main.js:45` AfterimagePass 把持续经过中心的亮刃拖成径向刺条，二者叠加成刺球；9s 一周期的 80 剑扫荡周期性加强它。
- 美学失败：待机是**吸引观众的第一画面、7×24 播放最久的画面**，其视觉主体却是一个语义不明的白色毛球；右上还有一个白月亮，画面像"两个太阳 + 坏掉的加载指针"，没有"万剑归宗于修士"的叙事。

**V2【致命】万剑齐发糊成白色海胆/折扇，读不出剑，且 0.65 秒就消失。**
- 根因链（A/B 两代理独立归因，主控核对代码一致）：64 剑在原点 ±1.1/±1.5 单位半径内**同点生成**（`swords.js:86-98`，角度 ±0.5rad 随机、速度随机）；加色半透明圆台外壳（opacity .18 AdditiveBlending，`:40-47`）在同一像素叠加直接加到白；bloom(threshold 0.75) 对 HDR 过曝核近似全开；Afterimage 再把 0.19s 内位置累积成放射线——**出生编排 + 加色叠加 + 全屏帧累积 + bloom 四重叠加**，不是换个颜色能救的。
- 数值模拟（peak≈0.85、寿命 1.1–1.7s、可视半高 6.53 世界单位）：中心出剑**可见时长中位仅 0.65s**（p10 0.50 / p90 0.93），寿命大部分在屏外耗尽；观众只看到"噗"地一闪。径向随机爆炸是**烟花语言**，不是"剑阵齐射"。单记 64 剑在 110 寸屏上只是"一簇闪光"（容量 1500、2 draw call，加数量近零成本，真正缺的是编队、层次与留屏时间）。

**V3【致命】本命剑是荧光棒/火柴，自带屏幕大小的蓝色水母影。**

**V4【致命】手部光环是靶心、冲击波是跨屏肥皂泡。**
- aura 双环 RingGeometry(0.5,.62)+(0.7,.84)，壁厚/半径达 21%，高速再放大 1.3–1.5 倍（`main.js:54-62,124-137`）——实拍像套在剑上的方向盘/救生圈；Rings 半径 1.2→**10**（直径 20 ≈ 可视宽 23.2 的 86%）、寿命 0.55s 全程可见（`swords.js:416-449`），约 **39% 寿命时间已超出上下屏边**，只剩跨角大残弧（v3_1.3 顶部/底部两道跨屏同心弧即此，常被误读为设计元素）；aura 跟锁平滑坐标、本命剑跟弹簧滞后坐标，二者分离（实拍"环里空空"）。

### 3.3 中/轻级（择要）

- **V11** AfterimagePass(damp 0.82) 是"糊"的总根源且按帧衰减不随 dt（30fps 残影时长翻倍，掉帧时更亮更白，性能↔观感劣化耦合）；震屏白噪声平移相机与全屏帧累积叠加，使月亮/远山/符文在 0.3s 震屏期整体出双影——**拖尾本该只属于剑**（B-N3）。
- **B-N2**：每记齐发全屏蓝白 radial 遮罩峰值 opacity .35、0.35s 冷却下连挥接近连续频闪，暗场展厅整屏爆白=廉价 PPT 感 + 光敏风险，且无 prefers-reduced-motion。
- **V12** 动态语言贫乏：剑只做刚体平移+朝向速度，无剑姿摆动、无"集结→悬停→齐射→归鞘"编排、无归鞘；待机仅匀速螺旋流入+9s 一横扫。
- **V13** 星野(320)/流萤(90)/火花(400)/剑尖/月华全用同一个 softDot 圆点加色，无形态/尺度/亮度层次。
- **V14** 天空 4×512 渐变拉伸可见横向 banding；暗角是 z=-44 一张死贴图，与雾/山无交互；超宽屏天空/暗角盖不住（B 代理 aspect 2.39 实证）。
- **V15/B-N5** 字体依赖系统 STKaiti/KaiTi（LTSC 精简系统缺楷体即整体 fallback，符文构造期不等 `document.fonts.ready`、只生成一次永不重绘）；无 OFL 嵌入。
- 轻级：两种金色不统一、分隔线 240px 写死、每帧 DOM 读写（main.js:155-157,212-216）、S 键 kiosk 下下载 PNG 且 rAF 外截图大概率黑帧（docs/03 M2-6，probe_sword.png 纯黑为实证）、F/S/M 无 `?debug=1` 门控、无 cursor:none/favicon/theme-color。
- **B-N7（测试取证注意）**：`?demo=1&t=x` 预滚后页面在 rAF 中继续用**墙钟** live 运行（swiftshader ~1fps 下每个 rAF 跳约 1 墙钟秒），web/shots 里 v3_*.png 的实际状态与文件名 t 并不一致（约含预滚后 4s 演化）——V1 白斑正是因此被此前各轮当成"齐发残留"。**视觉 A/B 回归必须改成"固定步长推进到 t 后冻结/单帧截获"，否则截图对比不可信。**

### 5.2 交互层→表现层事件契约（重构红线，字段全部可从现代码核实）

一个约 30 行的极简事件总线（`core/bus.js`），交互层**只发归一化语义事件，不做世界坐标换算、不 import three、不认识任何 FX 对象**：

| 事件 | 字段 | 现对应 |
|---|---|---|
| `session:state`（流） | `{state:'idle'\|'candidate'\|'locked', session, t}` | state 为**新增输出**（lock 内部态现仅布尔 present）；驱动待机演舞/候选弱反馈/"剑来"强反馈三档 |
| `session:acquire`（边沿） | `{session,nx,ny,t}` | 现 `acquired:true`——**当前全仓零消费**，重构必须接线（剑来+一次性法阵光效/音效） |
| `session:release`（边沿） | `{session,reason:'lost'\|'mirror'\|'stalled'\|'error'}` | 现 resetSession/超时释放，reason 新增 |
| `hand:frame`（流，~30fps） | `{nx,ny,vx,vy,speed,accepted,t}` | 现 onState；**世界坐标换算移到表现层**（顺手修 M-ANGLE 16.3° 分裂）；被拒/无新帧时速度应归零（现冻结，M-FB） |
| `gesture:burst`（边沿） | `{dx,dy,peak,nx,ny,t}` | 现 onSwipe；原点只给归一化手心，"剑位还是手心"由 FX 导演统一裁决（修 N6 半空炸开） |
| `health`（流/边沿） | `{trackFps,delegate:'gpu'\|'cpu',camera:'starting'\|'ok'\|'denied'\|'missing'\|'busy'\|'stalled',stalledSec}` | 现仅英文 status 串+HUD 数字；HUD/中文遮罩/看门狗都靠它 |

**不得绕过的红线**：①只有 `accepted` 帧可进挥舞检测器（换人跳变无法伪齐发的根本机制）；②锁的"最近有效帧龄"看门狗必须放在**视频帧门控之外、墙钟驱动**（否则 L1 冻结永久锁存会被原样搬进新架构）；③交互参数两版同步纪律（改 lock/config 必同步 config.py 并重跑 lock_check）；④镜像方向断言意图保留（但要先修 N-TEST-1 让它可信）。

### 5.4 关键选型裁决与性能预算

- **是否引入 postprocessing 库（B 反对/F 支持）**：主控裁决**有条件引入**——vendor pmndrs 预构建单 ESM（零依赖、Zlib、peer 兼容已核实），P0 阶段先做离线 importmap 冒烟与 4K 帧率/显存 A/B；若单文件 import 有障碍，回退用现有 ShaderPass 手写 selective bloom/god rays（B 的保守方案兜底），**不引入 npm 构建链**。
- **分辨率/显存（B、D 两代理按 r185 vendor 源码独立复算，静态推演待真机）**：4K（8.29MP，RGBA16F=8B/px）samples=4 ≈ **1.2–1.22GB**、samples=0 ≈ **0.45–0.49GB**；8K ≈ 4.87GB/1.96GB。当前每帧 3 次全分辨率 resolve、13 个全屏 RT 白配 depthBuffer（4K 白付约 73–96MB）。重构对策：设备像素**长边硬封顶 2560–3200**（dpr cap 对展厅 TV 常见 100% 缩放 dpr=1 零保护，docs/03 H5 前提修正继续有效）、samples=0 真机 A/B（暗场霓虹+bloom 下几何 AA 收益很小）、全屏 pass RT depthBuffer=false、软件渲染（SwiftShader/WARP）检测告警、`failIfMajorPerformanceCaveat`。
- **规模**：阵型 500–2000 实例（wanjian 实证 500/1dc/60fps 为作者自述待核；本项目现 CPU 上传 1500 槽仅 228KB/帧、JS<0.5ms，瓶颈在 GPU 填充，一期无需 GPGPU；万级/归宗回旋再上 GPUComputationRenderer）。
